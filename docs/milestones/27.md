## A1 — Prevent one reservation from authorizing multiple provider calls

### Current defect

`reserve_research_tokens()` returns an existing `RESERVED` row for an identical idempotency key.

Each caller receiving that row can then call:

```python
provider.generate_structured(request)
```

Two concurrent workers can therefore invoke the provider twice while sharing one reservation.

### Required design

Introduce an explicit provider-attempt execution claim.

Recommended reservation lifecycle:

```text
RESERVED
→ IN_FLIGHT
→ SETTLED
→ AMBIGUOUS
→ RELEASED
```

Allowed transitions:

```text
RESERVED → IN_FLIGHT
IN_FLIGHT → SETTLED
IN_FLIGHT → AMBIGUOUS
RESERVED → RELEASED
AMBIGUOUS → SETTLED
AMBIGUOUS → RELEASED
```

Do not permit:

```text
SETTLED → anything
RELEASED → anything
IN_FLIGHT → IN_FLIGHT by another owner
```

### Schema additions

Add only the fields necessary for a fenced claim:

```text
claim_owner
claim_generation
claimed_at
claim_expires_at
```

Use additive migration.

A simpler attempt-claim companion table is also acceptable if it avoids unsafe mutation of historical accounting fields.

The claim identity must be tied to the reservation ID.

### Atomic claim operation

Create a repository/domain operation such as:

````python
claim_research_token_attempt(
    conn,
    operation

Create a repository/domain operation such as:

```python
claim reservation_id,
    owner_id,
    now,
    expires_at,
) -> ClaimResult
````

It must use one conditional SQL update inside `BEGIN IMMEDIATE`:

```sql
UPDATE ...
SET status = 'IN_FLIGHT',
    claim_owner = ?,
    claim_generation = claim_generation + 1,
    claimed_at = ?,
    claim_expires_at = ?
WHERE reservation_id = ?
  AND status = 'RESERVED'
```

Only the worker that changes exactly one row may call the provider.

If the row is already `IN_FLIGHT`:

```text
TOKEN_ATTEMPT_ALREADY_IN_FLIGHT
```

Do not invoke the provider.

If the row is `SETTLED`, `AMBIGUOUS`, or `RELEASED`:

```text
TOKEN_RESERVATION_STATE_CONFLICT
```

Do not invoke the provider.

### Existing reservation reuse

Idempotent reservation reuse may still return the existing reservation.

But reuse must not itself authorize a provider invocation.

The controller must claim the reservation after reserve/reuse and before:

```python
provider.generate_structured(...)
```

Required sequence:

```text
reserve or load reservation
validate immutable payload
atomically claim RESERVED → IN_FLIGHT
invoke provider
settle or mark ambiguous using claim ownership/generation
```

### Fencing

Settlement and ambiguity transitions must verify:

```text
reservation_id
claim_owner
claim_generation
current status = IN_FLIGHT
```

A stale worker must not settle or mark ambiguous after another owner takes over.

Use bounded owner identifiers. Do not persist machine usernames, credentials, or raw process environment values.

### Claim expiration

Do not automatically re-run an expired `IN_FLIGHT` provider attempt.

An expired `IN_FLIGHT` claim means transmission may have occurred.

Required behavior:

```text
expired IN_FLIGHT
→ transition or classify as AMBIGUOUS
→ operator reconciliation required
→ no automatic provider retry
```

A maintenance/recovery function may perform:

```text
expired IN_FLIGHT → AMBIGUOUS
```

using an expected-state and generation check.

Do not use lease expiry as proof that the provider was never called.

### Provider exceptions

Handle provider outcomes conservatively:

```text
known validation/configuration failure before transmission
→ IN_FLIGHT → RELEASED only when the adapter proves no request was transmitted

timeout / interruption / malformed response / unknown transmission state
→ IN_FLIGHT → AMBIGUOUS

authoritative response with usage
→ IN_FLIGHT → SETTLED
```

Do not broadly release on every `ProviderUnavailableError` unless that error type proves pre-transmission failure RELEASED only when the adapter proves no request was transmitted

timeout / interruption / malformed response / unknown transmission state
→ IN_FLIGHT → AMBIGUOUS

authoritative response with usage
→ IN_FL.

If current provider exceptions cannot distinguish transmission state, default to `AMBIGUOUS`.

## A2 — Invoke legacy token migration automatically at startup

### Current defect

`migrate_legacy_token_reservations()` is only called manually by tests or direct callers.

Normal `connect()` does not run it.

### Required behavior

During database startup:

```text
apply shadow schema
run semantic legacy token migration
fail startup on migration conflict
continue only when migration is complete
```

The migration must run before any token-budget calculation or controller invocation.

### Integration location

Prefer one of these:

```text
apply_shadow_operations_schema()
```

or a versioned migration invoked from:

```text
connect()
```

Do not place it only in CLI commands because library callers also use the database.

### Atomic fail-closed migration

Refactor the migration into two phases inside one transaction:

1. Inspect and validate every legacy candidate.
2. If any conflict exists, raise and roll back.
3. If all rows are valid, migrate all rows.
4. Record a migration version or completion marker.
5. Commit.

Do not return successful migration results containing unresolved conflicts.

Raise a bounded error such as:

```text
TOKEN_MIGRATION_CONFLICT
TOKEN_MIGRATION_BUDGET_DATE_UNRESOLVED
TOKEN_MIGRATION_INCOMPLETE_METADATA
```

Do not expose raw row contents.

### Legacy row detection

Migrate only rows whose idempotency key begins with:

```text
research_token_budget:
```

Do not alter genuine cost reservations.

Preserve historical combined output allowance exactly.

Use:

```text
token_accounting_policy = REASONING_INCLUDED_IN_OUTPUT
reserved_reasoning_tokens = 0
consumed_reasoning_tokens = 0
```

unless authoritative historical evidence proves another representation.

### Idempotency

Opening the database repeatedly must:

```text
not rewrite already migrated rows
not double-count rows
not generate new migration records repeatedly
```

## B1 — Make retry rollover and retry checkpoint atomic

### Current defect

The retry path currently commits:

```text
prior reservation → SUPERSEDED_BY_RETRY
new attempt reservation → RESERVED
```

before it persists the next-attempt:

```text
SUBMISSION_REQUESTED
```

event.

A crash between those operations leaves:

```text
event chain still on attempt N UNKNOWN
attempt N reservation terminal SUPERSEDED_BY_RETRY
attempt N+1 reservation active RESERVED
no attempt N+1 event
```

The retry path then looks for an active reservation for attempt N and fails permanently.

### Required behavior

Persist all retry preparation state in one order-lease-fenced transaction:

```text
validate current event is UNKNOWN
validate exact authoritative unconsumed NOT_FOUND lookup
validate account fingerprint
validate preview
validate retry limit
validate new-day notional capacity
supersede prior reservation
create next-attempt reservation
append next-attempt SUBMISSION_REQUESTED event
bind/consume authoritative lookup
commit
```

Only after this transaction commits may the broker submission call occur.

No network or broker call may happen inside the transaction.

### Recommended implementation

Create a focused function such as:

```python
_prepare_external_retry_attempt(...)
```

Return:

```text
new attempt number
new reservation ID
new SUBMISSION_REQUESTED event
runtime request ID
```

The function must run inside the existing order-lease fenced transaction.

Avoid nesting `transaction()` inside `lease.fenced_write()`.

Refactor `_reserve_daily_notional()` if necessary so it can participate in a caller-owned transaction using:

```text
commit=False
```

or a transaction-free internal helper.

### Lookup consumption

Consume or bind the authoritative `NOT_FOUND` lookup in the same preparation transaction.

Otherwise a crash may allow the same lookup to prepare multiple retries.

The lookup should record the newly created retry event ID.

### Broker invocation

After the preparation transaction commits:

```text
heartbeat lease
call runtime.submit_limit_order
```

Then atomically persist:

```text
broker outcome event
order status
attempt reservation state
```

using the existing fenced transaction pattern.

## B2 — Restart recovery for a prepared retry

A crash after retry preparation but before the broker call leaves:

```text
current event = SUBMISSION_REQUESTED for attempt N+1
reservation = RESERVED for attempt N+1
lookup consumed by that retry event
```

This is a valid durable prepared state.

`recover_stranded_submission()` must handle it through authoritative broker lookup.

Required behavior:

```text
broker FOUND
→ synchronize order state
→ reservation becomes SUBMITTED
```

```text
broker authoritative NOT_FOUND
→ local state becomes UNKNOWN_REQUIRES_RECONCILIATION
→ reservation becomes RECONCILIATION_REQUIRED
→ explicit operator retry may later create attempt N+2
```

```text
lookup timeout or malformed response
→ UNKNOWN_REQUIRES_RECONCILIATION
→ reservation remains RECONCILIATION_REQUIRED
```

Do not automatically submit the already-prepared attempt after restart.

A `SUBMISSION_REQUESTED` state means transmission may have occurred.

## B3 — Preserve daily-cap semantics

For a cross-day retry:

```text
prior date attempt
→ SUPERSEDED_BY_RETRY
```

```text
new date attempt
→ RESERVED then SUBMITTED or RECONCILIATION_REQUIRED
```

If new-day capacity is insufficient:

```text
entire preparation transaction rolls back
prior reservation remains RECONCILIATION_REQUIRED
lookup remains unconsumed
no new attempt event
no new reservation
broker not called
```

For a same-day retry:

* do not double-count the prior and new attempt;
* rollover and cap calculation must remain atomic.
