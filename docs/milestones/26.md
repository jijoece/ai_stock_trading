## A1 — Enforce token reservations in production research paths

Current issue:

`analyze_with_research_committee()` still directly invokes:

```python
provider.generate_structured(request)
```

when no token-budget controller is supplied.

The scheduled research-cycle path does not accept or pass a token-budget controller.

Required behavior:

When a daily token cap is configured:

```text
fresh provider call
→ token-budget controller required
→ reservation required
→ provider invocation allowed
```

When no daily token cap is configured:

```text
existing backward-compatible direct invocation may remain
```

Do not make fixture-only or deterministic zero-cost providers require token reservations unless configuration explicitly enables the token cap for them.

### Scheduled-cycle changes

Add a parameter such as:

```python
token_budget_controller_factory:
    Callable[[str], ResearchTokenBudgetController] | None
```

The factory should receive enough stable context to construct a controller for the symbol or cycle.

Pass the resulting controller into:

```python
analyze_with_research_committee(...)
```

for every fresh research invocation.

### Fail-closed rule

When configuration says token budgeting is enabled but no controller is available:

```text
TOKEN_BUDGET_CONTROLLER_REQUIRED
```

Return or persist an analysis-incomplete/budget-gated result before any provider call.

Do not silently fall back to direct provider invocation.

### CLI wiring

For CLI paths capable of invoking a real or token-consuming provider:

* load the configured daily token cap;
* construct `PersistentResearchTokenBudgetController`;
* inject it into the scheduled cycle.

For deterministic fixture providers, either:

* disable token budgeting explicitly; or
* inject a controller according to the same configuration.

Do not hard-code a production token cap.

## A2 — Block ambiguous retries across UTC dates

Current issue:

Reservation idempotency includes the UTC budget date, and ambiguity lookup is restricted to the current budget date.

An unresolved July 19 attempt can therefore be retried on July 20 under a new reservation.

Required behavior:

Before creating a reservation, search for unresolved ambiguity across all dates for the same provider attempt identity:

```text
research_run_id
symbol
provider
model
role
attempt_number
```

Persist these components explicitly if parsing them from the idempotency key is fragile.

Recommended additive columns:

```text
research_run_id
symbol
provider_name
model_name
research_attempt_identity
```

Alternative:

Create a stable `provider_attempt_key` excluding the budget date.

Use:

```text
provider_attempt_key
+ budget_date
```

for reservation identity.

But ambiguity blocking must search only by:

```text
provider_attempt_key
```

across every date.

Required result:

```text
any AMBIGUOUS reservation for provider_attempt_key
→ reject new reservation
→ TOKEN_RESERVATION_RECONCILIATION_REQUIRED
```

Do not allow a new automatic retry merely because UTC date changed.

Add an index on the stable provider-attempt identity and status.

## A4 — Migrate pre-PR #35 token reservations

Current issue:

Existing `shadow_budget_reservations` rows were given the default:

```text

```

during schema upgrade.

Older token reservations whose idempotency keys begin with:

```text
research_token_budget:
```

therefore disappear from token-cap calculations.

Required migration:

Identify legacy token rows by their stable idempotency-key prefix.

Backfill:

```text
reservation_kind = RESEARCH_TOKENS
budget_date
token_accounting_policy
reserved_reasoning_tokens

```

### Budget date

Derive it only from authoritative persisted data.

Preferred order:

1. parse the legacy key’s UTC date suffix;
2. otherwise derive from timezone-aware `created_at`;
3. fail closed if neither is valid.

### Legacy output/reasoning representation

Older reservations may have combined:

```text

```

inside `reserved_output_tokens`.

Do not split historical combined values without evidence.

Use a conservative migrated policy, such as:

```text
REASONING_INCLUDED_IN_OUTPUT
```

and preserve the combined output total exactly.

Do not fabricate separate reasoning usage.

### Conflict handling

If a row already has token metadata:

* compare existing values;
* treat an identical migration as idempotent;
* fail closed on material conflict.

The migration must not alter cost-only reservations.

Add bounded migration error codes rather than exposing raw rows.

## A6 — Make repeated operator reconciliation truly idempotent

Current issue:

A second reconciliation to the same target state is accepted without checking whether the second evidence matches the first.

Required behavior:

A repeated reconciliation may return an idempotent no-op only when all authoritative fields match the persisted reconciliation:

```text
target status
actual input tokens
actual output tokens
actual reasoning tokens
token-accounting policy
provider request ID
reconciliation source
```

Operator and explanatory text may differ only if the system explicitly records a second append-only note without changing accounting.

Simplest safe behavior:

```text
same target + identical accounting evidence
→ idempotent success/no-op

same target + different accounting evidence
→ TOKEN_RECONCILIATION_EVIDENCE_CONFLICT
```

Do not silently accept contradictory usage.

For `AMBIGUOUS → RELEASED`, require the same authoritative proof identity on repeated calls.

## A7 — Avoid marking settled reservations ambiguous after settlement conflict

Review this flow:

```python
try:
    settle_research_tokens(...)
except TokenBudgetError:
    mark_research_tokens_ambiguous(...)
```

A settlement failure may occur because another process already settled the reservation.

Blindly calling `mark_research_tokens_ambiguous()` afterward can create another conflicting transition attempt.

Required behavior:

Classify settlement failures:

```text
compatible already-settled result
→ return provider response successfully

conflicting terminal state
→ fail closed
→ do not attempt another transition

reservation still RESERVED but usage cannot be persisted
→ transition to AMBIGUOUS
```

Reload the reservation after settlement failure before deciding.

Do not attempt `SETTLED → AMBIGUOUS`.
