## A1 — Fix cross-day retry accounting

Current problem:

A reservation is keyed only by `client_order_id`.

When a retry occurs on a later UTC date, `_reserve_daily_notional()` finds the previous reservation and returns it without charging the retry against the new date’s daily limit.

Example:

```text
July 19:
order becomes ambiguous
reservation date = July 19
state = RECONCILIATION_REQUIRED

July 20:
broker confirms NOT_FOUND
operator retries the same client_order_id

Current behavior:
old July 19 reservation is reused
July 20 daily cap is not charged
```

This must be fixed before multi-day soak testing.

## A2 — Represent reservations per submission attempt

Prefer a new immutable reservation identity:

```text
reservation_id
client_order_id
attempt_number
account_fingerprint
reservation_date
book_id
reserved_notional_usd
state
created_at
updated_at
```

Recommended deterministic identity:

```text
hash(
  client_order_id,
  attempt_number,
  account_fingerprint,
  reservation_date
)
```

Do not use only `client_order_id` as the primary key for daily-budget reservations.

One external order may have:

```text
attempt 0 reservation on July 19
attempt 1 reservation on July 20
```

but only under the existing explicit retry safety process.

## A3 — Cross-day retry transition

For an ambiguous reservation from a prior date:

1. Require authoritative broker `NOT_FOUND` evidence for the exact ambiguous attempt.
2. Require that evidence to be unconsumed and matched to:

   * client-order ID;
   * payload hash;
   * account fingerprint;
   * attempt number;
   * ambiguous event ID.
3. Under one atomic transaction:

   * resolve the old reservation so it no longer blocks future accounting;
   * reserve the retry notional against the current UTC date;
   * ensure the account-wide current-day total remains within the cap.
4. Commit before calling the broker.
5. On definite broker rejection, release the new reservation.
6. On ambiguous retry outcome, retain the new reservation as `RECONCILIATION_REQUIRED`.
7. On broker acceptance, settle it to `SUBMITTED`.

Do not release the original ambiguous reservation merely because the date changed.

Only authoritative `NOT_FOUND` evidence may resolve it as not submitted.

## A4 — Reservation states

Use explicit states such as:

```text
RESERVED
SUBMITTED
RELEASED
RECONCILIATION_REQUIRED
SUPERSEDED_BY_RETRY
```

`SUPERSEDED_BY_RETRY` may only be used after authoritative `NOT_FOUND` confirms that the previous attempt did not create a broker order.

A reservation in any unresolved state must continue counting against its own reservation date.

## A5 — Atomicity

The following must happen in one `BEGIN IMMEDIATE` transaction:

```text
validate prior attempt retry eligibility
validate authoritative NOT_FOUND evidence
calculate current-day reserved/submitted total
resolve prior reservation
create current-day retry reservation
mark lookup evidence consumed or bound to retry
```

Avoid this unsafe sequence:

```text
release old reservation
commit
later create new reservation
```

A crash between those operations could lose budget accounting.

Reuse existing transaction and fenced-write conventions.

Do not introduce nested transactions on the same connection.

## A6 — Same-day retries

A same-day retry should not reserve the same notional twice.

Expected behavior:

```text
same UTC date
same client-order ID
same retry attempt identity
→ reuse current attempt reservation
```

A different retry attempt must still be uniquely represented and must not create duplicate broker submissions.

## B4 — Align price confirmation with the selected event

Current problem:

The event strategy uses the latest close versus the immediately previous close, regardless of the event date.

`confirmation_window_days` does not currently define the actual event-response period.

Required flow:

1. Deterministically select one qualifying event.
2. Identify its market timing.
3. Find the last valid pre-event reference bar.
4. Find the first tradable post-event bar.
5. Find the latest confirmation bar within the configured confirmation window.
6. Calculate the response from the pre-event reference to the confirmation bar.
7. Calculate volume confirmation over the post-event confirmation window.
8. Apply the maximum-extension guard to the event-aligned move.

## B5 — Event selection rule

Select the most recent qualifying positive event, not the oldest.

Recommended deterministic ordering:

```text
published_timestamp descending
effective_timestamp descending
event_timestamp descending
event_id ascending as final tie-break
```

Use the timestamp that represents when the information became knowable to the market.

Do not let an older event mask a newer material event.

If multiple recent events conflict:

```text
recent material negative event
→ NOT_ELIGIBLE
```

Preserve the existing fail-closed conflict rule.

## B6 — Event market-timing alignment

Handle at least these cases deterministically:

### Event published during market hours

Use the most recent completed bar that was available before publication as the reference.

Do not use the same daily close when the event occurred before that close unless intraday data exists and is explicitly supported.

With daily bars only, use a conservative next-session confirmation policy.

### Event published after market close

Reference:

```text
that session's completed close
```

First tradable confirmation session:

```text
next market session
```

### Weekend or market-holiday event

Reference:

```text
last completed market session before publication
```

First confirmation session:

```text
next available market session
```

Do not use calendar-day arithmetic as a substitute for market sessions.
