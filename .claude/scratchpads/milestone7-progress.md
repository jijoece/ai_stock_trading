## Shadow-operations design
**Milestone 7 core slice (this session, docs/milestone-7.md Steps 12-17; ADR 0005 Decisions 3-6):**
- `config/shadow_operations.yaml` + `src/trading_research/shadow/config.py::load_shadow_operations_config()` — same fail-closed, `hash_config`-stamped pattern as `research/scheduled_research_config.py`/`evidence_providers/config.py`. `shadow_operations.enabled: false` and `schedule.enabled: false` ship disabled. `allow_enhanced_submission` is structurally impossible to be `true` — `ShadowOperationsSection.__post_init__` raises `ShadowOperationsConfigError` if it is ever `true`, mirroring `PromotionGateConfig.allow_live_promotion`. Unknown `mode`/`cadence` fail closed against a `KNOWN_MODES`/`KNOWN_CADENCES` allowlist. No environment variable is read anywhere in the module — `.env` never decides a capability, only ever supplies a credential (repository-wide convention, unchanged).
- `src/trading_research/shadow/lease.py` — database-backed lease over the new `shadow_run_leases` table. `acquire`/`renew`/`release`/`force_release` all wrap their read-then-write in an explicit `conn.execute("BEGIN IMMEDIATE")` transaction, which takes a real SQLite file-level write lock for the duration — verified safe across two independent `sqlite3.connect()` calls against the same on-disk file (not `:memory:`) in `tests/unit/test_shadow_lease.py`'s concurrency tests. Stale reclaim (an expired lease can be taken by a new owner) uses a conditional `UPDATE ... WHERE expires_at < ?` and checks `cursor.rowcount` to detect a race against a second concurrent stale-reclaim attempt; the winning reclaim always writes a `shadow_operator_actions` row via `_record_stale_recovery` (`action_type=LEASE_STALE_RECOVERED`) — never a silent takeover. `force_release` is the only way to release a lease without presenting the owner token, and raises unless both `reason` and `operator` are non-empty; it always records a `LEASE_FORCE_RELEASED` operator action.
- `src/trading_research/shadow/pause.py` — single current-state row (`shadow_pause_state.is_current=1`) plus append-only history, exactly per ADR 0005 Decision 4. `storage/shadow_operations_repositories.py::insert_pause_state` demotes the previous current row and inserts the new one inside one implicit transaction so exactly one row is ever current. States: `ACTIVE`, `PAUSED_MANUAL`, `PAUSED_BUDGET`, `PAUSED_PROVIDER_HEALTH`, `PAUSED_RESEARCH_QUALITY`, `PAUSED_RECONCILIATION`, `KILLED`. `resume()` and `request_pause()` both raise `PauseStateError` while current state is `KILLED`; the only exit from `KILLED` is `force_clear_kill(reason, operator, clock)`, which always writes a `KILL_FORCE_CLEARED` operator action. `source` field distinguishes `OPERATOR` vs `AUTOMATIC_HEALTH_RULE` (the latter's caller — a deterministic health-rule evaluator — is explicitly later work; this module only supports the field). Structural fact, asserted by an AST-based test (`test_pause_module_has_no_provider_or_research_imports`): `pause.py` imports nothing from `evidence_providers`/`research.orchestration`/`research.scheduled_cycle`/`anthropic` — no model or provider output can reach pause/kill decisions because the module cannot see it.

## Budget and cost-control design
**Milestone 7 core slice (this session, docs/milestone-7.md Step 16-17; ADR 0005 Decisions 5-6):**
- `src/trading_research/shadow/budget.py` — `estimate_cycle_cost(intent, pricing_entries, as_of_date)` computes worst-case tokens/latency as `max_symbols_per_cycle * max_roles_per_symbol * max_attempts_per_role * max_{output,input}_tokens_per_cycle`, reusing `research/usage.py::select_pricing` (no second pricing table). When `intent.provider == "anthropic"` and no pricing entry matches, raises `BudgetConfigError` — this is the structural block that stops a real-Claude estimate (and therefore any downstream reservation/call) before it can proceed. `deterministic`/`scripted` providers are exempt (`estimated_cost_usd=None`, `pricing_required=False`), matching Milestone 6's existing cost-tracking scope.
- `reserve_budget(conn, idempotency_key, intent, estimate, max_actual_cost_per_day_usd, max_actual_cost_per_month_usd, clock)` is idempotent on `idempotency_key` (`shadow_budget_reservations.idempotency_key` has a `UNIQUE` constraint; a second call with the same key returns the existing row rather than inserting). Remaining daily/monthly budget is computed as `cap - settled_usage_for_period - sum(still-RESERVED reservations)` — concurrent live reservations are counted, not just settled usage, closing the race where two concurrent cycles could each see "budget available" against the same cap.
- `record_actual_usage(...)` accepts actual cost/tokens/latency from the caller (never computed or fabricated inside this module) and accumulates them onto the reservation's `consumed_*` columns plus an append-only `shadow_budget_usage` row (queryable by `usage_date` prefix for daily/monthly rollups).
- `settle_reservation` (idempotent — settling twice is a no-op) and `expire_abandoned_reservations(conn, clock, max_age_seconds)` (a sweep marking still-`RESERVED` rows older than `max_age_seconds` as `EXPIRED`, for crash recovery) both act only on `shadow_budget_reservations.status`.
- `check_emergency_margin_breach(conn, reservation_id, emergency_margin_fraction)` reports (never acts on) whether `consumed_cost_usd > reserved_estimated_cost_usd * (1 + margin)`; sets `emergency_margin_breached=1` on the row when true. The caller (later work) decides whether to request a pause — matches ADR 0005 Decision 7's "detect vs act" separation, same as `evaluate_cycle_health` will.
- `src/trading_research/shadow/role_budget.py::check_role_budget(...)` is the Step 17 pre-call gate: checks allowed-role membership, `role_index < max_roles_per_symbol`, `attempt_number <= max_attempts_per_role`, then compares the role's *configured maximum possible* input/output tokens, latency, and derived worst-case cost against `remaining_reservation_budget(conn, reservation_id)` (a `budget.py` accessor: `reserved_* - consumed_*` per dimension). Any check that would exceed remaining budget returns `RoleBudgetDecision(decision=SKIPPED_BUDGET_EXHAUSTED, ...)` — a dataclass with no `failure_code`/`provider_failure` field shared with the research-failure taxonomy, so it cannot be structurally conflated with a provider failure downstream. `RoleBudgetDecision.__post_init__` fails closed on any decision value outside `{PROCEED, SKIPPED_BUDGET_EXHAUSTED}`.

**Alerts/health/readiness slice (this session, 2026-07-13) — Steps 21-23:**
- `OperationalAlert` frozen dataclass (`shadow/alerts.py`): severity (INFO/WARNING/ERROR/CRITICAL), one of the 17 exact alert_type strings named in the milestone doc, message (bounded to 1000 chars, truncated not rejected), context (bounded dict, secret-shaped keys/values stripped via `sanitize_context`), created_at (tz-aware, required), a deterministic `dedup_key` computed from `alert_type` + a sorted/stringified context subset (SHA-256, stable across process runs).
- `AlertSink` is a `typing.Protocol` (`send(alert) -> AlertDeliveryResult`), not `runtime_checkable` — matches this repo's existing Protocol usage style (structural typing for the two concrete sinks, no `isinstance` checks anywhere in production code).
- Two concrete sinks shipped: `PersistenceOnlyAlertSink` (trivial no-op `send`, since `raise_alert` already persisted before any sink runs) and `LogAlertSink` (structured log line via `logging_config.get_logger`, subject to the same `redact()` secret-scrubbing every other log line gets). No webhook/email sink — confirmed against ADR 0005 Decision 8's "no concrete, already-authorized target" reasoning; this repo has zero existing outbound-HTTP-notification dependency to build on.
- `raise_alert(conn, alert, sinks, clock, dedup_window_seconds, max_delivery_attempts)`: persists to `shadow_alerts` unconditionally before touching any sink (proven by `test_alert_persisted_even_when_every_sink_raises`); checks `dedup_key` against `shadow_alerts` rows created within `dedup_window_seconds` — a duplicate is not re-persisted and not re-delivered, but increments `suppressed_count` on the original row (never a silent drop, proven by `test_suppressed_duplicate_still_recorded_via_suppressed_count`); each sink gets up to `max_delivery_attempts` (default 2 — one initial attempt plus one bounded retry, never unbounded) with every attempt (success or failure) persisted to `shadow_alert_deliveries` (sink_name, attempt_number, success, bounded response_text).
- A `CRITICAL` alert whose delivery fails on every sink is still fully queryable via `load_alert`/`list_alerts` and its failed attempts are all visible in `shadow_alert_deliveries` — proven by `test_critical_alert_failing_every_sink_is_still_queryable` (2 sinks x 2 attempts = 4 recorded failed-delivery rows, alert row itself untouched/undeleted).
- `shadow/health.py::evaluate_cycle_health` is a pure function (no DB/network import at all in the function body; module-level import of `shadow.pause` exists only for the separate `apply_health_result` function below it) taking `CycleHealthInputs` (provider success rate, evidence completeness, Claude role success, retry/retry-exhaustion/unsupported-claim rates, output-truncation rate, latency, tokens, cost + `pricing_configured` flag, paper-reconciliation-mismatch flag, duplicate-prevention-violation flag, cycle duration, budget-breached flag) and `HealthPolicyConfig` (thresholds sourced 1:1 from `config/shadow_operations.yaml`'s existing `safety.*` section via `HealthPolicyConfig.from_shadow_config`, plus `max_cycle_duration_seconds` reused from `budgets.max_latency_seconds_per_cycle` — no second config file introduced), producing `HEALTHY`/`DEGRADED`/`PAUSE_RECOMMENDED`/`PAUSE_REQUIRED` with a tuple of exact reasons and a tuple of `triggering_flags` naming which specific `safety.pause_on_*` dimension(s) drove a `PAUSE_REQUIRED` verdict. `None` inputs (e.g. no Claude roles ran this cycle) never fabricate a 0.0/1.0 — they simply do not contribute a failure signal.
- `DEGRADED` uses a fixed fraction (0.6x) of each configured pause threshold as its own "approaching the line" threshold — this module's own versioned interpretation, since the milestone doc only names the `pause_on_*` thresholds explicitly, not a second DEGRADED tier.

## Bugs discovered and fixed
- (this session, Steps 4-7/11 slice) `corporate_status_adapters._latest_of` initially matched form types by exact string (`ANNUAL_FORM_TYPES = ("10-K", "10-K405", "20-F")`), which meant an amendment filing ("10-K/A") never matched the annual-filing category at all — `latest_annual_filing` silently fell back to an earlier non-amendment 10-K even when the amendment was the most recently accepted annual-category filing. Caught by `test_amendment_form_type_retained` (test_corporate_status.py) failing with `'10-K' == '10-K/A'` before the fix. Fixed by adding `_base_form_type()` (strips a trailing `/A` for category-membership tests only) while still preserving the verbatim `form_type` and `is_amendment=True` on the returned `FilingReference` — the amendment is correctly categorized as an annual filing without collapsing away the fact that it *is* an amendment.
- (news/corporate-actions/Reddit slice, this session) **Pre-existing latent bug found in `cli.py::_build_evidence_provider_registry`'s sentiment wiring**, fixed as part of this slice: the prior code was `RedditSentimentSource(credentials_configured=provider_config.sentiment.enabled)` — this gates `credentials_configured` on the *YAML config-file flag* (`config/evidence_providers.yaml`'s `sentiment.enabled`), not on actual `REDDIT_CLIENT_ID`/`REDDIT_CLIENT_SECRET` presence. This meant that flipping `sentiment.enabled: true` in the config file alone (with no Reddit credentials anywhere) would have produced a `RedditSentimentSource` reporting `credentials_configured=True` while having no `fetch_records` callable — which `RedditSentimentSource.fetch` already defends against (`test_configured_sentiment_source_without_fetch_callable_still_fails_closed` in `test_evidence_adapters_fail_closed.py` covers exactly this shape and still passes), so the prior code was not exploitable into fabricated data, but it *was* semantically wrong: "configured" should mean "credentials present," not "operator flipped a YAML flag." Fixed by routing through the new `reddit_fetch.build_reddit_sentiment_source(cfg)`, which checks `config.reddit_client_id`/`config.reddit_client_secret` directly. No test in the existing suite broke (the fail-closed behavior was already correct at the `RedditSentimentSource` layer); this is a correctness/clarity fix at the wiring layer, not a regression fix.
- (news/corporate-actions/Reddit slice, this session) Two new tests initially asserted `"forbidden_string" not in module_source_text`, which false-failed because the forbidden strings appeared in the module's own docstring (documenting *why* those tools/imports are excluded), not in actual code. Fixed by switching both to AST-based checks (parsing string-literal constants and import statements specifically, not raw substring search over the whole file including docstrings/comments) — `test_reddit_fetch.py::test_reddit_fetch_module_never_calls_mutation_tools`, `test_no_claude_import_in_reddit_fetch_module`, and `test_corporate_actions.py::test_never_infers_action_from_price_data`. **Shadow-operations core slice (this session):**
- `shadow/lease.py::acquire`'s stale-reclaim path initially checked `conn.total_changes == 0` after the conditional `UPDATE ... Caught before any test ran against it by re-reading the SQL semantics while writing the concurrency test; fixed by using `cursor.rowcount` from the `UPDATE` statement's own returned cursor instead, which correctly reports 0 exactly when the conditional `WHERE expires_at < ?` matched no row (i.e., another connection already reclaimed or renewed it first within the transaction window). **Scheduler-orchestrator slice (this session):**
- A significant design bug caught and fixed entirely during test-writing, before any test was reported passing: `shadow/schedule.py::resolve_due_status`'s first draft walked the actionable catch-up window **today-first**, which meant a genuinely missed prior-day slot could never be reported — today's own (more recent) status always won the race, silently swallowing backlog. Caught by `test_missed_yesterday_within_catchup_is_reported_today` failing (`DUE` instead of the expected `MISSED_WITHIN_CATCHUP`). Fixed by reordering the window walk to oldest-first.
- A second, subtler bug in the same function: once reordered oldest-first, a *first-ever run* (`last_completed_intended_time=None`) started incorrectly reporting `MISSED_TOO_OLD` for dates up to 30 days in the past, because the "is this slot completed" check only understands a monotonic watermark, not "never ran before." Fixed by gating the entire `MISSED_TOO_OLD` lookback-margin check on `last_completed_intended_time is not None` — a first-ever run has no meaningful backlog and starts fresh.
